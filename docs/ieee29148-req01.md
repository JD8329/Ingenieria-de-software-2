# Especificación del requisito HU-01 — Registro de agricultores

**Proyecto:** AgroValle Connect
**Requisito:** REQ-HU01-REG-001
**Versión:** 1.0
**Estado:** especificación derivada del backlog y contrastada con el backend disponible
**Trazabilidad:** HU-01 de [`BACKLOG.md`](../BACKLOG.md)

> Este documento organiza HU-01 como un requisito de sistema formal, verificable
> y trazable, tomando como referencia el enfoque de ingeniería de requisitos de
> ISO/IEC/IEEE 29148:2018. No declara certificación ni conformidad completa con
> la norma. Los requisitos describen el alcance observado en el repositorio y
> hacen explícitas las decisiones que todavía deben acordarse con el Product
> Owner.

## 1. Propósito

Especificar el comportamiento del sistema para que una persona no registrada
pueda crear una cuenta de agricultor en AgroValle Connect. La especificación
sirve como base para diseño, implementación, pruebas y trazabilidad.

## 2. Contexto y alcance

El sistema ofrece el endpoint REST `POST /api/v1/agricultores/registro`. La
solicitud se valida, se comprueba que no exista previamente el correo ni la
cédula, se codifica la contraseña y se persiste un agricultor con rol
`PRODUCCION`.

Este requisito cubre únicamente el registro del agricultor. No cubre registro
de comerciantes, recuperación de contraseña, verificación de correo, activación
de cuenta, inicio de sesión ni registro de lotes.

## 3. Actores e interesados

| Actor o interesado | Responsabilidad o interés |
|---|---|
| Agricultor no registrado | Envía sus datos para crear una cuenta. |
| Sistema AgroValle Connect | Valida, evita duplicados, protege la contraseña y persiste el registro. |
| Product Owner / equipo | Confirma reglas de negocio, datos obligatorios y criterios de aceptación. |

## 4. Interfaces y datos

**Interfaz:** `POST /api/v1/agricultores/registro`
**Formato de entrada:** JSON
**Respuesta de éxito:** `201 Created`, con una representación del agricultor registrado.

| Campo de solicitud | Obligatorio | Restricción implementada |
|---|---:|---|
| `nombreCompleto` | Sí | No puede estar vacío. |
| `cedula` | Sí | De 6 a 10 dígitos numéricos. |
| `correo` | Sí | No vacío y formato de correo válido. Debe ser único. |
| `contrasena` | Sí | No vacía y con un mínimo de 8 caracteres. |
| `telefono` | No | Sin otra restricción declarada en el DTO actual. |
| `ubicacionFinca` | Sí | No puede estar vacía. |
| `municipio` | Sí | Debe corresponder a un valor del enum `Municipio`. |

Municipios aceptados por el backend: `DAGUA`, `PALMIRA`, `BUGA`, `TULUA`,
`CAICEDONIA` y `JAMUNDI`. El rol se asigna internamente como `PRODUCCION`; no
se acepta como campo elegido por el cliente.

## 5. Requisitos funcionales

Los términos **DEBE** y **NO DEBE** expresan requisitos obligatorios dentro del
alcance descrito.

| ID | Requisito del sistema | Prioridad | Verificación |
|---|---|---|---|
| REQ-HU01-001 | El sistema DEBE exponer el registro de agricultores mediante `POST /api/v1/agricultores/registro`. | Must | Prueba de integración del endpoint. |
| REQ-HU01-002 | El sistema DEBE aceptar una solicitud JSON con nombre completo, cédula, correo, contraseña, ubicación de finca y municipio; el teléfono DEBE ser opcional. | Must | Casos de solicitud válida y teléfono omitido. |
| REQ-HU01-003 | El sistema DEBE rechazar la solicitud con `400 Bad Request` cuando falte un campo obligatorio, el correo no tenga formato válido, la cédula no tenga entre 6 y 10 dígitos o la contraseña tenga menos de 8 caracteres. | Must | `registrarAgricultorSinCamposObligatorios_Retorna400`, `registrarAgricultorConCorreoInvalido_Retorna400`, `registrarAgricultorConCedulaFueraDeRango_Retorna400` y `registrarAgricultorConContrasenaCorta_Retorna400`. |
| REQ-HU01-004 | El sistema DEBE rechazar con `400 Bad Request` un valor de municipio que no pertenezca al catálogo definido por el enum `Municipio`. | Must | `registrarAgricultorConMunicipioInvalido_Retorna400`. |
| REQ-HU01-005 | El sistema NO DEBE registrar dos agricultores con el mismo correo o con la misma cédula. | Must | `registrarAgricultorConCorreoDuplicado_Retorna409` y `registrarAgricultorConCedulaDuplicada_Retorna409`. |
| REQ-HU01-006 | Cuando el correo o la cédula ya estén registrados, el sistema DEBE responder `409 Conflict` y no crear un segundo agricultor. | Must | Prueba de duplicado y verificación de persistencia. |
| REQ-HU01-007 | Para una solicitud válida y única, el sistema DEBE persistir el agricultor en la base de datos y asignarle internamente el rol `PRODUCCION`. | Must | Prueba de integración y lectura posterior desde el repositorio. |
| REQ-HU01-008 | El sistema DEBE almacenar la contraseña usando un codificador seguro de contraseñas y NO DEBE persistirla en texto plano. | Must | Comparar hash almacenado y contraseña original; verificar `PasswordEncoder.matches`. |
| REQ-HU01-009 | Si el registro se completa, el sistema DEBE responder `201 Created` con el identificador y los datos de respuesta definidos por el contrato del endpoint. | Must | Verificación del estado y del cuerpo HTTP. |
| REQ-HU01-010 | La respuesta del registro NO DEBE incluir la contraseña ni su hash. | Must | Afirmar que `contrasena` y `password_hash` no existen en el JSON. |
| REQ-HU01-011 | La persistencia DEBE mantener únicas las columnas de correo y cédula, incluso si dos solicitudes concurrentes superan la comprobación previa del servicio. | Must | `persistenciaRechazaCorreoDuplicadoAunqueSeOmitaValidacionDelServicio` y `persistenciaRechazaCedulaDuplicadaAunqueSeOmitaValidacionDelServicio` comprueban las restricciones de base de datos. |

## 6. Requisitos no funcionales y restricciones

| ID | Requisito |
|---|---|
| REQ-HU01-NF-001 | La contraseña solo se almacenará mediante BCrypt; la API no expondrá contraseña ni hash. |
| REQ-HU01-NF-002 | Las reglas de entrada se validarán en el límite REST usando Bean Validation y el DTO de registro. |
| REQ-HU01-NF-003 | La persistencia se realizará con Spring Data JPA. PostgreSQL es la base configurada para ejecución y H2 se utiliza en las pruebas automatizadas. |
| REQ-HU01-NF-004 | El endpoint de registro será accesible sin token JWT para permitir la creación inicial de una cuenta. |
| REQ-HU01-NF-005 | Los errores de entrada inválida y conflicto serán distinguibles mediante los códigos HTTP `400` y `409`, respectivamente. |

## 7. Precondiciones y postcondiciones

**Precondiciones**

- La aplicación está iniciada y puede conectarse a la base de datos.
- El cliente envía JSON interpretable por la API.
- El endpoint de registro está disponible públicamente.

**Postcondiciones en caso de éxito**

- Existe un registro de agricultor persistido con identificador generado.
- La cédula y el correo quedan asociados de manera única.
- La contraseña queda codificada y no aparece en la respuesta.
- El rol del agricultor es `PRODUCCION`.
- La respuesta HTTP es `201 Created`.

**Postcondiciones ante rechazo**

- No se crea un nuevo registro.
- La respuesta indica error de validación (`400`) o conflicto por duplicidad
  (`409`).

## 8. Escenario BDD asociado

**Historia de usuario**

> Como agricultor, quiero registrarme en la plataforma ingresando mi cédula,
> nombre y finca por municipio, para ofrecer mis cosechas directamente a
> comercios urbanos.

**Escenario: registro correcto**

- **Given** que un agricultor no registrado accede al endpoint
  `/api/v1/agricultores/registro`.
- **When** envía un JSON con nombre completo, cédula válida, correo válido,
  contraseña de al menos ocho caracteres, ubicación de finca y municipio
  permitido.
- **Then** el sistema responde `201 Created`, persiste la información, asigna el
  rol `PRODUCCION` y no devuelve la contraseña.

**Escenario: correo o cédula duplicados**

- **Given** que ya existe un agricultor con el correo o la cédula enviados.
- **When** se solicita el registro con ese dato repetido.
- **Then** el sistema responde `409 Conflict` y no crea otro registro.

**Escenario: datos inválidos**

- **Given** una solicitud que omite un dato obligatorio o incumple una regla de
  validación.
- **When** se envía la solicitud de registro.
- **Then** el sistema responde `400 Bad Request` y no persiste el agricultor.

## 9. Matriz de trazabilidad

| Requisito | Componente relacionado | Evidencia automatizada disponible |
|---|---|---|
| REQ-HU01-001, 002, 007, 009, 010 | `AgricultorController`, `AgricultorService`, `AgricultorResponse` | `registrarAgricultorValido_Retorna201YNoExponeContrasena` |
| REQ-HU01-003 | `AgricultorRegistroRequest`, `GlobalExceptionHandler` | Pruebas de campos obligatorios, correo, cédula y contraseña inválidos con respuesta `400`. |
| REQ-HU01-004 | `AgricultorRegistroRequest`, `GlobalExceptionHandler` | Prueba de integración con municipio fuera del enum; respuesta `400` y sin persistencia. |
| REQ-HU01-005, 006 | `AgricultorService`, `AgricultorRepository` | Pruebas independientes de duplicidad de correo y cédula; ambas esperan `409`. |
| REQ-HU01-011 | Restricciones `unique` de `Agricultor` y base de datos | Pruebas de persistencia intentan insertar cada dato duplicado sin pasar por las validaciones previas del servicio; la base rechaza ambos casos. |
| REQ-HU01-008 | `AgricultorService`, `PasswordEncoder` | La prueba de registro verifica que la contraseña persistida no es texto plano y que `PasswordEncoder.matches` funciona. |

La suite se ejecuta con `./mvnw test`; `./mvnw clean verify` agrega Checkstyle y
la comprobación de cobertura configurada. Las pruebas de integración de HU-01
comprueban éxito, campos obligatorios, formatos, municipio permitido,
duplicidades de correo/cédula, persistencia y protección de la contraseña. La
matriz acredita las restricciones únicas de persistencia sin simular el
intercalado temporal de dos solicitudes concurrentes.

## 11. Límites del alcance documentado

- Esta especificación refleja el contrato validado por el backend del Sprint 1:
  cédula de 6–10 dígitos, municipio del enum actual y respuesta que excluye la
  contraseña, pero incluye cédula y correo.
- La fecha de cosecha pertenece a HU-02 y se acepta si es hoy o futura, según
  la validación implementada; no es una regla de HU-01.
- La unicidad bajo condiciones de carrera depende de las restricciones únicas
  de la base de datos. Las pruebas fuerzan inserciones duplicadas directamente,
  pero no simulan el intercalado temporal de solicitudes concurrentes.
